# Tickle 시연 시나리오

## 1. 시연 개요

시연은 OBS 화면을 기준으로 실제 운영 서버에 웹과 모바일이 각각 접속된 상태에서 진행합니다. 전체 흐름은 서비스 소개, 부하테스트, 부하 상황 예매 플로우, 봇 탐지 순서로 진행합니다.

| 단계 | 제목 | 핵심 장면 |
|------|------|-----------|
| STEP 1 | 사이트 소개 | 운영 서버의 웹/모바일 메인 화면, 인기 공연, 오픈 예정 공연, 공연 상세 정보 |
| STEP 2 | 부하테스트 시작 | 관리자 페이지에서 1,000명 가상 유저 접속 시작, 대기자 수 증가 확인 |
| STEP 3 | 부하 상황 예매 플로우 | 대기자가 200명 이상 쌓인 상태에서 일반 사용자가 예매 진입, 대기열, CAPTCHA, 결제 완료 |
| STEP 4 | 봇 탐지 | 기존 티켓팅 환경에서 동작하는 매크로 비교 후 Tickle에서 동일 매크로 탐지/차단 확인 |

## 2. 시연 전 준비

### 2.1 화면 준비

| 구분 | 준비 화면 | 목적 |
|------|-----------|------|
| OBS 메인 장면 | 실제 운영 서버 웹 화면과 모바일 화면 | 웹/모바일 동시 접속 상태를 보여줌 |
| 사용자 웹 화면 | Tickle 메인 화면 `/` | 공연 탐색, 상세 진입, 예매 플로우 진행 |
| 사용자 모바일 화면 | Tickle 모바일 화면 | 운영 서버에 모바일로도 접속된 상태 확인 |
| 실시간 현황 관리자 화면 | 관리자 대시보드 | 대기열 현황과 실시간 접속자 수 확인 |
| 봇 탐지 관리자 화면 | `/admin/bot-detection` | 매크로 탐지 후 탐지/차단 내역 확인 |
| 매크로 비교 화면 | 인터파크 환경 또는 사전 준비된 비교 시연 화면 | 기존 티켓팅 서비스에서 자동화 접근이 가능한 장면 비교 |

### 2.2 데이터 준비

| 항목 | 준비 내용 |
|------|-----------|
| 시연 공연 | 메인 화면에서 클릭 가능한 공연 1건 |
| 공연 상세 | 공연 정보, 가격 정보, 공연 일정이 정상 노출되는 상태 |
| 좌석 상태 | 대부분 매진/비활성 상태, 6~7개 좌석만 선택 가능하도록 준비 |
| 사용자 계정 | 예매를 진행할 일반 사용자 로그인 완료 |
| 관리자 계정 | 관리자 페이지 접근 가능 |
| 부하테스트 | 관리자 페이지에서 1,000명 가상 유저 접속 버튼 실행 가능 |
| 결제 | 테스트 결제 또는 mock 결제 완료 흐름 준비 |
| 매크로 시연 | 기존 티켓팅 환경 비교용 매크로 실행 준비, Tickle 적용 시 탐지/차단 확인 가능 |


## 3. 상세 시연 순서

## STEP 1. 사이트 소개

### 목적

운영 서버에 웹과 모바일이 접속된 상태를 먼저 보여주고, Tickle 메인 화면과 공연 상세 화면을 소개합니다.

### 실행 순서

| 순서 | 화면 | 실행/클릭 위치 | 확인 및 설명 |
|------|------|----------------|--------------|
| 1 | OBS 장면 | 웹 화면과 모바일 화면이 동시에 보이는 영역 | 실제 운영 서버에 웹/모바일로 각각 접속한 상태임을 설명 |
| 2 | 메인 화면 `/` | 홈 화면 전체 | Tickle 메인 화면 소개 |
| 3 | 메인 화면 `/` | 인기 공연 목록 영역 | 현재 가장 인기 있는 공연 목록을 한눈에 볼 수 있음을 설명 |
| 4 | 메인 화면 `/` | 오픈 예정 공연 목록 영역 | 오픈 예정 공연을 확인할 수 있음을 설명 |
| 5 | 메인 화면 `/` | 시연 공연 카드 클릭 | 특정 공연 상세 화면으로 이동 |
| 6 | 공연 상세 화면 `/detail` | 공연 정보 영역 | 공연명, 포스터, 장소 등 기본 공연 정보 확인 |

### STEP 1 완료 기준

- 웹/모바일 운영 서버 접속 상태가 OBS에 보입니다.
- 메인 화면에서 인기 공연과 오픈 예정 공연이 보입니다.
- 공연 상세 화면에서 공연 정보, 가격 정보, 공연 일정이 확인됩니다.

## STEP 2. 부하테스트 시작

### 목적

관리자 페이지에서 1,000명의 가상 유저 접속 플로우를 실행하고, 대기열 현황과 실시간 접속자 수가 증가하는 것을 확인합니다.

### 실행 순서

| 순서 | 화면 | 실행/클릭 위치 | 확인 및 설명 |
|------|------|----------------|--------------|
| 1 | 관리자 페이지 | 관리자 페이지로 화면 전환 | 부하테스트와 실시간 모니터링을 위해 관리자 화면으로 이동 |
| 2 | 관리자 페이지 | 왼쪽 대기열 현황 영역 | 공연의 대기열 현황을 실시간으로 볼 수 있음을 설명 |
| 3 | 관리자 페이지 | 오른쪽 실시간 접속자 수 대시보드 | 현재 접속자 수를 대시보드로 확인할 수 있음을 설명 |
| 4 | 관리자 페이지 | `부하테스트 시작` 버튼 | 1,000명의 가상 유저 접속 시작 |
| 5 | 관리자 페이지 | 대기열 현황 영역 | 현재 대기자 수가 실시간으로 증가하는지 확인 |
| 6 | 관리자 페이지 | 대기자 수 지표 | 대기자가 200명을 넘는 시점까지 증가 추이를 확인 |

### STEP 2 완료 기준

- 부하테스트가 시작됩니다.
- 대기자 수가 실시간으로 증가합니다.
- 대기자 수가 200명 이상으로 증가한 시점에 STEP 3으로 진입합니다.

## STEP 3. 부하테스트 상황에서 실제 예매 플로우 시연

### 목적

대기자가 쌓인 상황에서 실제 사용자도 동일한 예매 플로우를 진행하고, 대기열 반영, CAPTCHA 인증, 결제 완료까지 확인합니다.

### 실행 순서

| 순서 | 화면 | 실행/클릭 위치 | 확인 및 설명 |
|------|------|----------------|--------------|
| 1 | 사용자 공연 상세 화면 `/detail` | `예매하기` 버튼 클릭 | 부하테스트가 진행 중인 상태에서 일반 사용자도 예매 진입 |
| 2 | 대기열 화면 | 대기 순번/대기자 수 표시 영역 | 사용자가 대기열에 들어가고 대기열 상태가 실시간 반영되는지 확인 |
| 3 | 대기열 화면 | 입장 허용 상태 | 본인 순서가 올 때까지 잠시 대기 |
| 4 | CAPTCHA 화면 | CAPTCHA 인증 영역 | 본인 순서가 오면 CAPTCHA 인증 진행 |
| 5 | 예매 화면 | 날짜/회차 선택 영역 | 시연용 공연 회차 선택 |
| 6 | 좌석 선택 화면 | 남은 좌석 1개 클릭 | 대부분 매진된 상태에서 남은 좌석을 선택 |
| 7 | 좌석 선택 화면 | `다음` 또는 `선택 완료` 버튼 | 좌석 선점 후 다음 단계 이동 |
| 8 | 권종/수량 화면 | 권종 선택 영역 | 일반권 등 권종 선택 |
| 9 | 결제 정보 화면 | 약관 동의 및 결제 수단 선택 | 결제 진행 준비 |
| 10 | 결제 화면 | `카카오페이로 결제하기` 버튼 | 테스트 결제 완료 |
| 11 | 결제 완료 화면 | 예매 완료 정보 | 티켓팅 플로우 완료 확인 |
| 12 | 관리자 페이지 | 실시간 접속자 수 대시보드 | 접속자 수가 1,001명으로 반영되는지 확인 |

### STEP 3 완료 기준

- 사용자 화면에서 대기열 진입이 확인됩니다.
- 본인 순서 도달 후 CAPTCHA 인증을 진행합니다.
- 좌석 선택과 결제 완료 화면까지 진행됩니다.
- 관리자 대시보드에서 1,000명 가상 유저와 시연자 1명을 포함한 1,001명 접속 상태가 확인됩니다.

### 시연 포인트

| 포인트 | 설명 |
|--------|------|
| 대기열 반영 | 예매하기 버튼 클릭 즉시 사용자가 대기열에 반영됨 |
| 안정성 | 1,000명 이상 동시 접속 상황에서도 예매 플로우가 유지됨 |
| 실시간성 | 관리자 대시보드의 대기자 수와 접속자 수가 실시간 갱신됨 |

## STEP 4. 봇 탐지 시연

### 목적

기존 티켓팅 환경에서 동작하는 매크로를 비교 장면으로 먼저 보여준 뒤, 동일한 자동화 접근이 Tickle에서는 탐지되어 차단되는 것을 확인합니다.

### 실행 순서

| 순서 | 화면 | 실행/클릭 위치 | 확인 및 설명 |
|------|------|----------------|--------------|
| 1 | 발표/사용자 화면 | 티켓팅 시연 종료 후 봇 탐지 시연으로 전환 | “다음으로 실제 매크로 탐지 여부를 확인”하는 흐름으로 전환 |
| 2 | 타 티켓팅 플랫폼의 공연 예매 화면 | 준비된 매크로 실행 | 기존 티켓팅 환경에서 자동화 도구가 티켓팅 서비스에 접근하는 장면 확인 |
| 3 | 타 티켓팅 플랫폼의 공연 예매 플로우 | 공연 선택, 예매 진입, 결제 직전 단계 | 매크로가 손을 대지 않아도 예매 플로우를 진행하는 장면 확인 |
| 4 | Tickle 메인 화면 `/` | Tickle 서비스로 화면 전환 | 동일 매크로를 Tickle에 적용할 준비 |
| 5 | Tickle 화면 | 준비된 매크로 실행 | 매크로가 Tickle 공연/예매 플로우에 접근 시도 |
| 6 | Tickle 사용자 화면 | 차단 안내, CAPTCHA, 또는 `/blocked` 화면 | 인터파크 비교 환경에서 동작한 매크로가 Tickle에서는 탐지/차단되는지 확인 |
| 7 | 관리자 봇 탐지 화면 `/admin/bot-detection` | 봇 탐지 대시보드 | 탐지 수와 차단 수가 증가하는지 확인 |
| 8 | 관리자 봇 탐지 화면 `/admin/bot-detection` | 최근 차단 내역 | 어떤 유저가 매크로를 사용했는지 확인 |
| 9 | 관리자 봇 탐지 화면 `/admin/bot-detection` | 탐지 그래프, AI 점수 구간 | 매크로 탐지 이벤트가 대시보드 통계에 반영되는지 확인 |

### STEP 4 완료 기준

- 기존 티켓팅 비교 환경에서는 매크로가 예매 흐름에 접근하는 장면이 보입니다.
- 같은 자동화 접근이 Tickle에서는 탐지되어 차단됩니다.
- 관리자 봇 탐지 대시보드에서 탐지 사용자, 탐지 수, 차단 수, 최근 차단 내역이 확인됩니다.

### 시연 포인트

| 포인트 | 설명 |
|--------|------|
| 비교 명확성 | 기존 티켓팅 환경에서는 자동화 접근이 결제 직전까지 진행됨 |
| Tickle 차별점 | 동일 자동화 패턴이 Tickle에서는 탐지/차단됨 |
| 관리자 가시성 | 어떤 사용자가 매크로를 사용했는지 관리자 화면에서 확인 가능 |
| 실시간 반영 | 봇 탐지 결과가 대시보드에 실시간 반영됨 |

## 5. 장애 대응 플랜

| 상황 | 대응 |
|------|------|
| OBS 웹/모바일 화면 중 하나가 보이지 않음 | 해당 브라우저를 새로고침하고 OBS 소스 활성화 여부 확인 |
| 부하테스트 수치 반영이 늦음 | 관리자 페이지 새로고침 후 10초 대기 |
| 대기자가 200명까지 증가하지 않음 | 부하테스트 재실행 또는 목표 유저 수/증가 속도 설정 확인 |
| 좌석이 모두 매진됨 | 예비 공연 또는 예비 회차로 전환 |
| Tickle 매크로 차단이 늦게 반영됨 | 관리자 봇 탐지 화면 새로고침 후 최근 차단 내역 확인 |
| 비교 환경 시연이 실패함 | 사전 녹화 화면으로 대체 |

## 6. 최종 시연 타임라인

| 구간 | 예상 시간 | 진행 내용 |
|------|-----------|-----------|
